# 17. OAuth 2.0

> OAuth는 사용자가 비밀번호를 넘겨주지 않고도 다른 애플리케이션에 자기 계정의 일부 권한만 위임할 수 있게 하는 표준이다. "구글로 로그인", "카카오로 시작하기"가 대표적인 예다.

## 핵심 요약

- OAuth 2.0은 **인가(authorization)**, 즉 권한을 위임하는 프로토콜이다. 로그인(인증)에 쓸 때는 그 위에 **OpenID Connect(OIDC)** 를 함께 쓴다.
- 서버가 있는 웹 서비스는 **인가 코드 방식** 을, 모바일 앱과 SPA는 **인가 코드 + PKCE** 를, 서버 간 통신은 **클라이언트 자격 증명** 방식을 쓴다.
- 보안의 핵심: **HTTPS 필수**, **`state` 로 CSRF 방지**, **리다이렉트 URI 정확히 일치**, 시크릿과 리프레시 토큰은 **서버에만 보관**.
- 인가 서버를 직접 구현하기보다 검증된 서비스(구글, 카카오, Auth0, Keycloak 등)와 라이브러리를 쓴다.

> **참고** **인증(authentication)** 은 "당신이 누구인가"를 확인하는 것이고, **인가(authorization)** 는 "무엇을 해도 되는가"를 허락하는 것이다. OAuth 2.0이 주는 액세스 토큰은 "이 API를 호출해도 된다"는 허가증이지, "이 사람이 누구다"라는 증명은 아니다.

## OAuth 1.0a와 2.0

| 구분 | OAuth 1.0a | OAuth 2.0(RFC 6749, 2012) |
| --- | --- | --- |
| 요청 보호 | 모든 요청에 HMAC-SHA1 서명을 만들어 붙임 | HTTPS를 전제로 서명 없이 **Bearer 토큰** 전송 |
| 구현 난이도 | 파라미터 정렬·인코딩·서명이 까다로워 실수가 잦음 | 단순함 |
| 클라이언트 환경 | 웹 서버 중심 | 웹, 모바일, SPA, 서버 간, 기기별 **권한 부여 방식** 제공 |
| 토큰 수명 | 오래 유지 | 짧은 액세스 토큰 + 리프레시 토큰 |
| 서버 구성 | 하나의 서버 | 인가 서버와 리소스 서버 분리 가능 |

- 2.0은 1.0a와 호환되지 않는 새 프로토콜이다. 구현은 쉬워졌지만, 그만큼 보안이 HTTPS와 올바른 구현에 크게 의존한다.

## 기본 용어

| 용어 | 설명 | 예 |
| --- | --- | --- |
| 리소스 소유자 | 보호된 데이터의 주인 | 사용자 |
| 클라이언트 | 사용자를 대신해 데이터에 접근하려는 앱 | 우리 서비스 |
| 인가 서버 | 사용자를 인증하고 동의를 받아 토큰을 발급 | 구글·카카오의 OAuth 서버 |
| 리소스 서버 | 토큰을 확인하고 데이터를 제공하는 API 서버 | 구글 캘린더 API |
| 클라이언트 ID / 시크릿 | 인가 서버에 앱을 등록할 때 받는 식별자와 비밀 값 | 시크릿은 서버에만 보관 |
| 리다이렉트 URI | 사용자가 동의한 뒤 돌아올 우리 서비스의 주소 | `https://myservice.com/callback` |
| 스코프 | 요청하는 권한의 범위 | `profile`, `email`, `calendar.readonly` |
| 인가 코드 | 동의 후 발급되는 일회용 코드. 토큰으로 교환한다 | 수명 수십 초~수 분 |
| 액세스 토큰 | API 호출에 쓰는 토큰 | 수명 수 분~수 시간 |
| 리프레시 토큰 | 액세스 토큰이 만료되면 새로 발급받는 데 쓰는 토큰 | 수명이 길어 더 안전하게 보관 |

## 인가 코드 방식의 흐름

```text
사용자(브라우저)            우리 서비스(클라이언트)        인가 서버(예: 구글)       리소스 서버(API)
     │ 1. "구글로 로그인" ──────> │                              │                        │
     │ <── 2. 인가 서버로 리다이렉트 │                              │                        │
     │ ─────────────── 3. 로그인 및 권한 동의 ─────────────────> │                        │
     │ <────── 4. redirect_uri?code=인가코드&state=... ──────────── │                        │
     │ ── 5. 인가 코드 전달 ─────> │                              │                        │
     │                           │ ── 6. 코드 + 시크릿 ────────> │                        │
     │                           │ <── 7. 액세스(리프레시) 토큰 ── │                        │
     │                           │ ── 8. Authorization: Bearer 토큰 ───────────────────> │
     │                           │ <── 9. 사용자 정보 등 데이터 ─────────────────────────── │
```

1. 사용자가 "구글로 로그인" 버튼을 누른다.
2. 우리 서비스는 사용자를 인가 서버의 동의 화면으로 보낸다. `client_id`, `redirect_uri`, `scope`, `state`, `response_type=code` 를 쿼리 문자열로 전달한다.

    ```text
    https://accounts.example.com/oauth/authorize?response_type=code&client_id=abc123
        &redirect_uri=https://myservice.com/callback&scope=profile%20email&state=xyz789
    ```

3. 사용자는 인가 서버에서 로그인하고 요청된 권한에 동의한다. 비밀번호는 인가 서버에만 입력하므로 우리 서비스는 알 수 없다.
4. 인가 서버가 사용자를 `redirect_uri` 로 돌려보내며 인가 코드와 `state` 를 붙여 준다.
5. 우리 서버는 받은 `state` 가 2단계에서 보낸 값과 같은지 확인한다.
6. 우리 서버는 인가 코드와 `client_secret` 을 인가 서버의 토큰 엔드포인트로 보낸다. 이 요청은 브라우저를 거치지 않고 **서버와 서버 사이** 에서 직접 이루어진다.
7. 인가 서버가 코드와 시크릿을 확인하고 액세스 토큰(필요하면 리프레시 토큰)을 발급한다.
8. 우리 서비스는 `Authorization: Bearer <액세스 토큰>` 헤더를 붙여 API를 호출한다.
9. 리소스 서버는 토큰이 유효하고 스코프가 맞는지 확인한 뒤 데이터를 응답한다.

- 토큰을 바로 주지 않고 인가 코드를 한 번 거치는 이유: 브라우저 주소창이나 방문 기록에 남는 리다이렉트 URL에 토큰을 노출하지 않기 위해서다. 인가 코드는 한 번만 쓸 수 있고 수명도 매우 짧다.

## 그 밖의 권한 부여 방식

| 방식 | 사용하는 곳 | 설명 |
| --- | --- | --- |
| 인가 코드 + **PKCE** | 모바일 앱, SPA(지금은 모든 클라이언트에 권장) | 요청마다 임의의 `code_verifier` 를 만들고 그 해시(`code_challenge`)를 먼저 보낸 뒤, 토큰 교환 때 원래 값으로 증명한다. 시크릿을 안전하게 보관할 수 없는 앱도 안전하게 쓸 수 있다 |
| 클라이언트 자격 증명 | 사용자가 없는 서버 간 통신 | 클라이언트 ID와 시크릿만으로 토큰을 받는다 |
| 디바이스 코드 | 스마트 TV처럼 입력이 불편한 기기 | 화면의 코드를 휴대폰에서 입력해 승인한다 |
| 암시적(Implicit), 비밀번호(Password) | **사용 금지** | 보안 문제로 OAuth 2.1 초안에서 제거되었다 |

## 사용 시 주의할 점

- **HTTPS 필수**: 요청 서명이 없으므로, 토큰이 평문으로 전송되면 탈취되어 그대로 쓰인다([16장](../ch16_https/README.md)).
- **`state` 로 CSRF 방지**: 추측할 수 없는 난수([6장](../ch06_random/README.md))를 세션에 저장해 두고 콜백에서 비교한다. 이를 빠뜨리면 공격자가 자신의 인가 코드를 피해자 브라우저에 넣어, 피해자를 공격자 계정에 연결시킬 수 있다.
- **리다이렉트 URI 정확히 일치**: 와일드카드나 부분 일치를 허용하면 인가 코드가 공격자의 사이트로 전달될 수 있다.
- **비밀 값은 서버에만**: 클라이언트 시크릿과 리프레시 토큰을 앱 바이너리, 프런트엔드 자바스크립트, 소스 코드 저장소에 넣지 않는다.
- **최소 스코프**: 꼭 필요한 권한만 요청한다. 과도한 권한은 사용자의 동의율을 떨어뜨리고, 토큰이 유출되었을 때 피해를 키운다.
- **토큰 수명과 폐기**: 액세스 토큰은 짧게 유지하고, 로그아웃이나 비밀번호 변경 때 토큰을 폐기(revoke)한다. 브라우저에 저장해야 한다면 자바스크립트가 읽을 수 없는 `HttpOnly` 쿠키를 고려한다([14장](../ch14_http/README.md)).
- **로그인에는 ID 토큰 검증**: 로그인 용도라면 OIDC의 ID 토큰을 받아 서명, 발급자(`iss`), 대상(`aud`), 만료(`exp`)를 검증한다.
- **응답 데이터 이스케이프**: 인가 서버나 리소스 서버에서 받은 데이터를 화면에 출력할 때는 이스케이프하고, JSON 응답에는 `Content-Type: application/json` 을 정확히 지정한다. 그래야 데이터에 섞인 악성 스크립트가 HTML로 해석되어 실행되는 XSS를 막을 수 있다.

## 예제 코드

- 이 장에는 별도 예제 코드가 없다. 파이썬에서는 `Authlib` 라이브러리로 Flask에 OAuth 2.0 클라이언트를 쉽게 붙일 수 있다.

## 더 알아보기

- **OpenID Connect**: OAuth 2.0 위에 사용자 정보와 ID 토큰을 표준화한 인증 계층
- **JWT(JSON Web Token)**: 액세스 토큰과 ID 토큰에 많이 쓰는 형식. 헤더·페이로드·서명을 base64url로 인코딩해 점(`.`)으로 잇는다([12장](../ch12_base64/README.md))
- **RFC 9700(OAuth 2.0 Security Best Current Practice)** 과 **OAuth 2.1** 초안: 최신 보안 권장 사항
