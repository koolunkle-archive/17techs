# 03. 날짜와 시간

> 예약 결제, 티켓 오픈, 주식 장 시작처럼 정해진 시각이나 주기에 맞춰 도는 작업이 많다. 이런 작업은 어떤 종류의 시간을 기준으로 삼느냐에 따라 버그가 생기기도 하고 막을 수도 있다.

## 핵심 요약

- 컴퓨터의 시간은 두 종류다. **단조 시간** 은 절대 뒤로 가지 않고, **실제 시간** 은 언제든 바뀔 수 있다.
- **경과 시간 측정과 짧은 주기 작업** 에는 단조 시간을, **특정 날짜·시각에 하는 작업과 화면 표시** 에는 실제 시간을 쓴다.
- 서비스를 이루는 모든 서버와 프로그램은 **UTC** 로 시간을 저장하고 주고받는다. 사용자에게 보여줄 때만 현지 시간대로 바꾼다.
- 서버들의 시계는 **NTP** 로 같은 시간 서버에 맞춘다.

## 타임스탬프

- **타임스탬프(Unix time)** 는 1970-01-01 00:00:00 UTC부터 흐른 초다. 시간대와 상관없이 전 세계에서 같은 값이다.
- 파이썬의 `time.time()` 은 소수점 아래까지(마이크로초 수준) 돌려준다. 다만 실제 정밀도는 운영체제와 하드웨어에 따라 다르다.

```python
import time
print(f"현재 시간(Unix epoch time): {time.time()}")
```

## 단조 시간과 실제 시간

| 구분 | 단조 시간(monotonic) | 실제 시간(wall clock) |
| --- | --- | --- |
| 값 | 기준 시점(보통 부팅)부터 흐른 시간 | 현재 날짜와 시각 |
| 바뀌는 경우 | 재부팅하면 초기화. 그 외에는 계속 증가 | NTP 동기화, 사용자 변경, 서머타임 |
| 뒤로 갈 수 있나 | 없다 | 있다 |
| 용도 | 경과 시간 측정, 타임아웃, 짧은 주기 작업 | 매월 1일 정산, 예약 시각 실행, 로그·화면 표시 |
| 파이썬 | `time.monotonic()`, `time.perf_counter()` | `time.time()`, `datetime.now(timezone.utc)` |

### 단조 시간

- 운영체제가 하드웨어 타이머로 계산하며, 사용자가 시계를 바꿔도 영향을 받지 않는다.
- 값 자체(예: 12345.6초)에는 의미가 없고, 두 값의 **차이** 만 의미가 있다. 재부팅하면 다시 작은 값부터 시작하므로 파일이나 DB에 저장해 두고 비교하면 안 된다.

```python
t1 = time.monotonic()
do_something()
print(f"걸린 시간: {time.monotonic() - t1}초")
```

### 실제 시간

- 실제 날짜와 일치하므로 "매월 1일", "2026-12-25 09:00" 같은 작업에 쓴다. 한 달은 28~31일이고 윤년도 있으므로, 한 달 이상 주기의 작업은 단조 시간으로 계산하지 않는다.
- 언제든 바뀔 수 있다는 점을 전제로 코드를 짠다. 시각이 갑자기 앞이나 뒤로 이동하면 끝나야 할 작업이 끝나지 않거나, 같은 작업이 두 번 실행될 수 있다.

> **실무 팁** "매월 1일 0시에 실행"처럼 실제 시간이 기준인 작업도, 그 시각이 되었는지 **확인하는 간격** 은 단조 시간으로 잰다. 또 실행 기록(마지막 실행 날짜)을 저장해 두면 시계가 바뀌어도 중복 실행을 막을 수 있다.

## 시간대(타임 존)

- 나라와 지역마다 쓰는 표준 시간이 다르다. 한국은 `UTC+9`(`Asia/Seoul`)이다.
- **UTC(협정 세계시)** 가 기준이 되는 표준 시간이다. GMT는 영국의 시간대 이름이고 UTC와 값은 거의 같지만, 표준을 가리킬 때는 UTC라고 쓰는 것이 맞다.
- 미국·유럽 등은 **서머타임(DST)** 때문에 1년에 두 번 시각이 한 시간씩 바뀐다. 이때 같은 현지 시각이 두 번 오거나 아예 없는 시각이 생긴다.

### 서버마다 시간대가 다르면 생기는 문제

- A 서버(`UTC+9`)가 "21:00에 실행"이라는 작업을 시간대 정보 없이 B 서버(`UTC`)에 보내면, B 서버는 자신의 21:00, 즉 한국 시각 다음 날 06:00에 실행한다.
- 서버마다 로그 시각의 기준이 달라 장애가 났을 때 여러 서버의 로그를 맞춰 보기 어렵다.

### 시간대를 다루는 원칙

1. 저장, 연산, 서버 간 통신은 **UTC** 로 한다.
2. 시각을 문자열로 주고받을 때는 시간대 정보를 포함한 **ISO 8601** 형식을 쓴다. 예: `2026-10-09T12:38:18Z`, `2026-10-09T21:38:18+09:00`
3. 사용자에게 보여줄 때만 사용자의 시간대로 바꾼다.

```python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

now_utc = datetime.now(tz=timezone.utc)               # 저장·연산용
now_seoul = now_utc.astimezone(ZoneInfo("Asia/Seoul")) # 화면 표시용
print(now_utc.isoformat(), now_seoul.isoformat())
```

> **주의** 파이썬의 `datetime.now()` 는 시간대 정보가 없는(naive) 값을 돌려준다. 이 값은 실행한 서버의 설정에 따라 의미가 달라지므로 서버 코드에서는 `datetime.now(tz=timezone.utc)` 를 쓴다. `datetime.utcnow()` 는 파이썬 3.12부터 사용 중단(deprecated)되었다. 윈도우에서 `zoneinfo` 를 쓰려면 `tzdata` 패키지가 필요하다.

## 더 알아보기

- **NTP**: 서버 시계를 시간 서버에 맞추는 프로토콜. 리눅스는 `chrony`, 윈도우는 `w32time` 이 담당한다.
- **2038년 문제**: 타임스탬프를 32비트 정수로 저장하면 2038-01-19에 넘친다. DB 컬럼과 바이너리 규격에서는 64비트를 쓴다.
- **윤초**: 유닉스 시간은 윤초를 세지 않는다. 대형 서비스는 윤초를 하루에 걸쳐 나눠 반영(leap smear)하기도 한다.
