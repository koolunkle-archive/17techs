# 16. HTTPS

> HTTPS는 HTTP 메시지를 TLS로 암호화해 주고받는 프로토콜이다. 오늘날 웹 서비스는 HTTPS를 기본으로 쓴다.

## 핵심 요약

- HTTPS는 **기밀성**(엿볼 수 없음), **무결성**(변조를 알아챔), **서버 인증**(진짜 서버인지 확인)을 보장한다. 기본 포트는 443이다.
- 핸드셰이크에서 **인증서와 비대칭키** 로 서버를 확인하고 세션 키를 만든 뒤, 실제 데이터는 빠른 **대칭키** 로 암호화한다.
- SSL은 폐기되었다. **TLS 1.2 이상**(가능하면 1.3)만 허용한다.
- 인증서는 웹 서버나 로드 밸런서에서 설정하고, **자동 갱신** 과 만료 알림을 반드시 설정한다.
- HTTPS는 전송 구간만 보호한다. 비밀번호 해시 저장, 입력 검증, 권한 검사는 여전히 필요하다.

## HTTPS를 사용하는 이유

- HTTP는 메시지를 평문 그대로 보낸다([14장](../ch14_http/README.md)). 같은 와이파이의 다른 사용자나 중간 네트워크 장비가 비밀번호, 쿠키, 개인정보를 그대로 볼 수 있다.
- 공격자가 사용자와 서버 사이에 끼어들어 가짜 서버 행세를 하는 **중간자 공격(MITM)** 도 가능하다.

| 보장하는 것 | 수단 | 막는 공격 |
| --- | --- | --- |
| 기밀성 | 대칭키 암호화 | 도청 |
| 무결성 | MAC / AEAD | 전송 중 변조 |
| 서버 인증 | 인증서와 전자 서명 | 가짜 서버, 중간자 공격 |

- 그 밖의 실무적인 이유
  - 브라우저는 HTTP 사이트에 "주의 요함" 경고를 표시한다. 위치 정보, 카메라, 서비스 워커 같은 기능은 HTTPS에서만 쓸 수 있다.
  - HTTP/2와 HTTP/3는 사실상 HTTPS에서만 동작한다.
  - 쿠키의 `Secure` 속성, OAuth 2.0([17장](../ch17_oauth/README.md)) 등 많은 보안 기능이 HTTPS를 전제로 한다.

> **참고** SSL(Secure Sockets Layer)은 보안 취약점 때문에 더 이상 쓰지 않는다. 그래도 관습적으로 "SSL 인증서"라고 부르는 경우가 많다. 실제로 쓰는 것은 TLS 1.2와 TLS 1.3이다.

## HTTPS의 구성 요소

### 대칭키 암호화

- 암호화와 복호화에 **같은 키** 를 쓴다(AES, ChaCha20).
- 빠르므로 실제 HTTP 메시지를 암호화하는 데 쓴다.
- 처음 만난 상대와 키를 안전하게 나눠 갖기 어렵다는 문제(키 배송 문제)가 있다.

### 비대칭키(공개키) 암호화

- **공개키** 와 **개인키** 한 쌍을 쓴다(RSA, ECC). 공개키는 누구에게나 공개하고, 개인키는 소유자만 보관한다.
  - 공개키로 암호화한 데이터는 짝이 되는 개인키로만 풀 수 있다.
  - 개인키로 만든 **전자 서명** 은 공개키로 검증할 수 있다. 데이터를 그 개인키 소유자가 만들었다는 증거가 된다.
- 대칭키보다 훨씬 느리다. 그래서 상대를 인증하고 대칭키를 안전하게 정하는 데에만 쓴다.

### 인증서와 인증 기관(CA)

- **인증서** 는 "이 공개키는 이 도메인의 것"이라는 사실을 **인증 기관(CA)** 이 전자 서명으로 보증한 문서다. 도메인, 서버 공개키, 유효 기간, 발급 기관, 서명이 들어 있다.
- 인증서의 두 가지 역할
  - 접속한 서버가 그 도메인의 진짜 서버임을 보장한다.
  - TLS 통신에 쓸 서버의 공개키를 클라이언트에 전달한다.
- 운영체제와 브라우저에는 신뢰하는 **루트 인증서** 가 미리 들어 있다. 클라이언트는 `서버 인증서 → 중간 인증서 → 루트 인증서` 로 이어지는 **인증서 체인** 의 서명을 차례로 검증한다.
- 만료되었거나, 도메인이 맞지 않거나, 신뢰할 수 없는 기관이 발급한 인증서면 브라우저가 경고 화면을 띄운다.

### 메시지 인증

- 메시지가 전송 중에 바뀌지 않았는지 확인하기 위해 해시 기반의 **MAC** 을 쓴다([7장](../ch07_hash/README.md)).
- TLS 1.3은 AES-GCM, ChaCha20-Poly1305처럼 암호화와 무결성 검증을 한 번에 하는 **AEAD** 방식만 쓴다.

## TLS 핸드셰이크

- TCP 연결을 맺은 뒤, HTTP 메시지를 보내기 전에 TLS 핸드셰이크로 암호화 방식과 키를 정한다. 아래는 TLS 1.2를 기준으로 단순화한 과정이다.

```text
클라이언트                                             서버
    │ ── 1. Client Hello ────────────────────────────> │  TLS 버전, 암호화 방식 목록, 난수, 접속할 도메인(SNI)
    │ <─ 2. Server Hello ───────────────────────────── │  선택한 버전과 암호화 방식, 난수
    │ <─ 3. Certificate ────────────────────────────── │  서버 인증서(공개키 포함)
    │    4. 인증서 체인 검증(서명, 도메인, 유효 기간)
    │ <─> 5. 키 교환(ECDHE) ────────────────────────> │  양쪽이 같은 세션 키를 계산(키는 전송하지 않음)
    │ <─> 6. Finished ──────────────────────────────> │  핸드셰이크 내용이 변조되지 않았는지 확인
    │ <══ 7. 세션 키(대칭키)로 암호화한 HTTP 통신 ══> │
```

1. **Client Hello**: 지원하는 TLS 버전, 암호화 방식(cipher suite) 목록, 난수를 보낸다. 접속할 도메인(SNI)도 함께 보내서, 한 서버가 여러 도메인을 운영해도 알맞은 인증서를 고를 수 있다.
2. **Server Hello**: 서버가 버전과 암호화 방식을 고르고 서버 난수를 보낸다.
3. **Certificate**: 서버가 인증서를 보낸다.
4. **인증서 검증**: 클라이언트가 인증서 체인을 검증한다.
5. **키 교환**: ECDHE 같은 알고리즘으로 양쪽이 같은 **세션 키** 를 계산한다. 세션 키 자체는 네트워크로 보내지 않는다.
6. **Finished**: 지금까지 주고받은 핸드셰이크 메시지가 변조되지 않았는지 서로 확인한다.
7. 이후 모든 HTTP 요청과 응답을 세션 키로 암호화한다.

- **TLS 1.3** 은 핸드셰이크 왕복을 2번에서 1번으로 줄였고, 안전하지 않은 옛 암호화 방식을 모두 없앴다. 이전에 연결한 서버라면 첫 요청부터 데이터를 보내는 0-RTT도 지원한다.

> **참고** ECDHE처럼 연결마다 새 키를 만드는 방식은 **전방 비밀성(forward secrecy)** 을 제공한다. 나중에 서버 개인키가 유출되어도, 예전에 녹화해 둔 암호화 통신은 풀 수 없다.

## 실무에서 HTTPS 적용하기

- **어디서 설정할까**: Flask 같은 애플리케이션 프레임워크보다 Nginx·아파치 같은 웹 서버나 로드 밸런서에서 설정하는 것이 안전하고 관리하기 쉽다([14장](../ch14_http/README.md)).
- **인증서 발급과 갱신**: Let's Encrypt는 무료 인증서를 자동으로 발급하는 인증 기관이다. certbot 같은 도구로 설치와 갱신을 자동화한다. 인증서 최대 유효 기간은 단계적으로 줄어 2029년에는 47일이 될 예정이라, 자동 갱신은 필수다. 만료로 인한 장애는 실무에서 자주 일어나므로 만료 알림도 설정한다.
- **HTTP 차단**: HTTP로 들어온 요청은 `301` 로 HTTPS 주소로 보내고, `Strict-Transport-Security`(**HSTS**) 헤더로 브라우저가 처음부터 HTTPS로만 접속하게 한다.
- **혼합 콘텐츠**: HTTPS 페이지에서 이미지나 스크립트를 HTTP로 불러오면 브라우저가 차단한다. 모든 리소스를 HTTPS로 불러온다.
- **개인키 보호**: 개인키 파일은 접근 권한을 최소화하고 소스 코드 저장소에 절대 넣지 않는다.
- **인증서 검증 끄지 않기**: 테스트하려고 `verify=False` 같은 옵션을 켠 코드를 운영 환경에 남기면 HTTPS를 쓰는 의미가 사라진다.

## 예제 코드

- 이 장에는 별도 예제 코드가 없다. 14장의 Flask 서버 앞에 Nginx를 두고 인증서를 설정하는 것이 일반적인 구성이다.

```sh
# 서버가 보내는 인증서 체인과 TLS 버전 확인
openssl s_client -connect example.com:443 -servername example.com
```

## 더 알아보기

- [SSL Labs Server Test](https://www.ssllabs.com/ssltest/): 내 서버의 TLS 설정 점수와 취약한 설정 점검
- **mTLS(상호 TLS)**: 서버와 클라이언트가 서로의 인증서를 확인한다. 서버 간 통신이나 내부망 보안에 쓴다.
- **인증서 투명성(CT)**: 발급된 모든 인증서를 공개 로그에 기록해 잘못 발급된 인증서를 찾아낸다.
