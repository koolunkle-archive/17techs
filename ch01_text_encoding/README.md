# 01. 문자열 인코딩

> 컴퓨터는 문자를 숫자(바이트)로만 저장한다. 어떤 규칙으로 문자를 바이트로 바꾸는지 알아야 "글자 깨짐"의 원인을 찾을 수 있다.

## 핵심 요약

- **문자 집합(charset)** 은 사용할 수 있는 문자의 목록(유니코드, ASCII 등)이고, **문자열 인코딩** 은 그 문자를 바이트로 바꾸는 규칙(UTF-8, UTF-16 등)이다.
- 새로 만드는 시스템은 **UTF-8** 을 사용한다. ASCII와 호환되고, 웹·JSON·리눅스의 사실상 표준이다.
- UTF-16(윈도우 API, 자바 내부)이나 EUC-KR(레거시 국내 서비스)을 써야 한다면, UTF-8과의 **변환 지점(경계)** 을 한 곳으로 정한다.
- **글자 수와 바이트 수는 다르다.** `"안녕하세요"` 는 5글자지만 UTF-8로는 15바이트다. 버퍼 크기·DB 컬럼 길이를 정할 때 반드시 구분한다.

## 문자 집합과 인코딩

- 컴퓨터는 `01000001` 같은 2진수만 다룬다. 이 값을 문자 `A` 로 보여줄지, 숫자 65로 다룰지는 미리 정한 규칙에 달려 있다.
- 초기 컴퓨터는 영어만 지원했고, 이후 나라마다 독자적인 규칙(한국은 EUC-KR)을 만들었다. 같은 바이트를 다른 규칙으로 읽으면 글자가 깨진다.
- 이 문제를 해결하기 위해 전 세계 문자를 하나의 번호 체계로 모은 것이 **유니코드** 다. 유니코드는 문자마다 **코드 포인트**(예: `가` = `U+AC00`)를 부여하고, 이 번호를 바이트로 바꾸는 방식이 UTF-8, UTF-16, UTF-32다.

## 인코딩 비교

| 인코딩 | 한 글자 크기 | ASCII 호환 | 주 사용처 |
| --- | --- | --- | --- |
| ASCII | 1바이트(7비트, 128자) | - | 모든 인코딩의 기반 |
| EUC-KR / CP949 | 영문 1바이트, 한글 2바이트 | O | 레거시 국내 시스템 |
| UTF-8 | 1~4바이트(가변) | O | 웹, JSON, 리눅스, 대부분의 라이브러리 |
| UTF-16 | 2 또는 4바이트 | X | 윈도우 API, 자바·C#·자바스크립트 문자열 내부 |
| UTF-32 | 4바이트 고정 | X | 거의 사용하지 않음 |

### ASCII

- 영문 대소문자, 숫자, 공백, 특수 문자, 제어 문자를 0~127(7비트)로 표현한다. 오늘날에는 1바이트(8비트)에 담아 사용한다.
- 숫자 문자도 별도 코드가 있다. 문자 `'0'` 은 48, `'9'` 는 57이다.
- 영어 외의 언어는 표현할 수 없다.

### EUC-KR과 CP949

- **EUC-KR** 은 한국 산업 표준(KS X 1001) 한글 문자 집합을 쓰는 인코딩이다. ASCII 문자는 1바이트, 한글은 2바이트로 표현한다.
- 완성형이라 미리 정의된 2,350자의 한글만 표현할 수 있다. `똠`, `햏` 같은 글자는 표현하지 못한다.
- **CP949** 는 마이크로소프트가 EUC-KR을 확장해 한글 11,172자를 모두 표현할 수 있게 만든 인코딩이다. 실무에서 "EUC-KR"이라고 부르는 것은 대부분 CP949다.

### UTF-8

- 코드 포인트 범위에 따라 1~4바이트를 사용한다. 처음 128자는 ASCII와 완전히 같으므로 영어 텍스트는 ASCII 파일과 동일하다.

| 코드 포인트 범위 | 바이트 수 | 예 |
| --- | --- | --- |
| `U+0000` ~ `U+007F` | 1 | 영문, 숫자 |
| `U+0080` ~ `U+07FF` | 2 | 라틴 확장, 그리스어, 키릴 문자 |
| `U+0800` ~ `U+FFFF` | 3 | 한글, 한자, 일본어 |
| `U+10000` ~ `U+10FFFF` | 4 | 이모지, 고대 문자 |

> **참고** 초기 규격은 최대 6바이트까지 정의했지만, 2003년 RFC 3629에서 유니코드 범위(`U+10FFFF`)에 맞춰 최대 4바이트로 제한했다.

### UTF-16

- 유니코드는 17개의 **평면(plane)** 으로 나뉜다. 그중 자주 쓰는 문자가 모인 0번 평면을 **기본 다국어 평면(BMP, `U+0000` ~ `U+FFFF`)** 이라고 한다. 한글과 한자도 BMP에 있다.
- UTF-16은 BMP 문자를 2바이트로, 그 밖의 문자(이모지 등)를 4바이트로 표현한다.
- 4바이트 문자는 **서로게이트 쌍(surrogate pair)** 으로 표현한다. 앞 2바이트는 `0xD800` ~ `0xDBFF`, 뒤 2바이트는 `0xDC00` ~ `0xDFFF` 범위의 값을 사용하므로, 이 범위를 보면 4바이트 문자의 시작인지 알 수 있다.
- 자바, C#, 자바스크립트의 문자열 길이는 UTF-16 단위로 센다. 그래서 이모지 하나의 `length` 가 2로 나온다.

### UTF-32

- 모든 문자를 4바이트로 표현한다. 코드 포인트 값을 그대로 저장하므로 서로게이트 쌍이 없다.
- 공간 낭비가 커서 파일이나 통신에는 거의 쓰지 않는다.

## 바이트 순서 표시(BOM)

- 2바이트 이상을 한 단위로 쓰는 UTF-16과 UTF-32는 CPU에 따라 바이트를 저장하는 순서가 다르다.
  - **빅 엔디언(BE)**: 큰 자리 바이트를 먼저 저장한다. `안`(`U+C548`) → `C5 48`
  - **리틀 엔디언(LE)**: 작은 자리 바이트를 먼저 저장한다. `안`(`U+C548`) → `48 C5`
- 그래서 문자열 맨 앞에 `U+FEFF` 를 **BOM** 으로 붙여 순서를 알린다. `FE FF` 로 시작하면 빅 엔디언, `FF FE` 로 시작하면 리틀 엔디언이다.
- UTF-8은 1바이트 단위로 읽기 때문에 순서 문제가 없다. UTF-8 BOM(`EF BB BF`)은 쓰지 않는 것이 원칙이며, JSON은 BOM을 허용하지 않는다([8장](../ch08_json/README.md)).

> **주의** 윈도우 메모장이나 엑셀은 UTF-8 파일에 BOM을 붙이기도 한다. 이런 파일을 읽을 때 첫 키 이름 앞에 보이지 않는 문자가 붙어 파싱에 실패하면 BOM을 의심한다. 파이썬에서는 `encoding="utf-8-sig"` 로 읽으면 BOM을 제거해 준다.

## 글자 수와 바이트 수

- 사람 눈에 보이는 **글자 수** 와 메모리·파일에서 차지하는 **바이트 수** 는 인코딩에 따라 달라진다.

| 문자열 | ASCII | EUC-KR | UTF-8 | UTF-16(BOM 포함) |
| --- | --- | --- | --- | --- |
| `Hello`(5글자) | 5바이트 | 5바이트 | 5바이트 | 12바이트 |
| `안녕하세요`(5글자) | 표현 불가 | 10바이트 | 15바이트 | 12바이트 |

- 둘을 같다고 가정하는 코드에서 버그가 많이 생긴다. DB 컬럼 길이, 네트워크 버퍼, 문자열 자르기를 다룰 때는 무엇을 기준으로 세는지 확인한다.

## 실무에서 주의할 점

- **MySQL**: `utf8` 은 3바이트까지만 저장하므로 이모지를 넣으면 오류가 난다. `utf8mb4` 를 사용한다.
- **레거시 연동**: 일부 국내 결제·공공 API는 아직 EUC-KR(CP949)을 요구한다. 연동 모듈 안에서만 변환하고, 시스템 내부는 UTF-8로 유지한다.
- **파이썬 파일 입출력**: `open()` 은 운영체제 기본 인코딩을 쓴다(한국어 윈도우는 CP949). 항상 `encoding="utf-8"` 을 명시한다.

## 예제 코드

| 파일 | 내용 |
| --- | --- |
| `reading_bindata.py` | 같은 2진수(`0b01000001`)를 10진수, 16진수, 문자로 해석 |
| `ascii.py` | `Hello` 를 ASCII로 인코딩해 바이트 확인 |
| `euc-kr.py` | `안녕하세요` 를 EUC-KR로 인코딩(글자당 2바이트) |
| `utf-8.py` | 같은 문자열을 UTF-8로 인코딩(한글 글자당 3바이트) |
| `utf-16.py` | UTF-16 인코딩. 맨 앞의 BOM(`FF FE`, 리틀 엔디언) 확인 |

```sh
cd ch01_text_encoding
../.venv/Scripts/python.exe utf-8.py
```
